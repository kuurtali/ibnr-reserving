# IBNR Reserving

![Tests](https://img.shields.io/badge/tests-21-brightgreen)
![Python](https://img.shields.io/badge/python-3.10+-3776AB?logo=python&logoColor=white)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Quarterly **incurred chain ladder** reserving tool for non-life insurance —
development triangles, link ratios, tail extrapolation, ultimate loss and
IBNR, delivered as a formatted Excel report.

Built for the actual workflow of a reserving actuary rather than as a
textbook demonstration: it reads a claims table, handles paid vs
outstanding separately, respects the observation diagonal, and — the part
most homemade tools skip — **backtests its own past estimates.**

> **Data policy.** This repository contains no real portfolio data and
> cannot. The default input is synthetic (`data/ornek_hasar.xlsx`,
> generated by `data/uret.py`). Real data is supplied by environment
> variable only.

---

## What it does

```
claims table (Excel)
  → split into material / bodily-injury segments
  → cumulative paid + outstanding  =  incurred triangle
  → volume-weighted link ratios  (all / last 5y / last 3y)
  → tail factor  (manual, or log-linear decay extrapolation)
  → projection → ultimate → IBNR
  → factor-window scenarios + backtest
  → Excel report with charts
  → Tkinter UI, falls back to CLI when unavailable
```

### Design choices worth naming

**Volume-weighted, not simple average.** Link ratios are
`Σ C(i,j+1) / Σ C(i,j)`, so each accident period is weighted by its own
size. A simple average over-weights small, noisy periods.

**The observation diagonal is masked before projection.** Cells beyond the
valuation date are zeroed first. Skip this and stray forward-dated records
silently corrupt every factor.

**The tail is bounded.** Auto-extrapolation fits a log-linear decay to the
last factors, projects 20 steps forward, and **caps at 1.5**; if factors
aren't decaying it refuses and returns 1.0. Unbounded extrapolation is the
most common way tail factors go wrong.

**It backtests itself.** Re-runs the valuation 4, 8 and 12 quarters in the
past and compares what it *would* have estimated against what actually
developed. A reserving tool with no backtest is an opinion.

**Scenario table, not a single number.** All three factor windows are
computed side by side with percentage deviation from the base, because the
sensitivity of a reserve estimate to method choice is part of the answer.

## Verification

The synthetic generator builds the triangle from a **known** development
pattern, so the tool's output can be checked rather than eyeballed:

```
  d   expected    computed        diff
  0    1.45238    1.45238     1.3e-09
  1    1.18033    1.18033     6.2e-10
  2    1.10417    1.10417     5.0e-11
  ...
```

`tests/test_chain_ladder.py` asserts this, plus: tail = 1 leaves the
ultimate equal to the last column, a larger tail increases the ultimate,
out-of-diagonal cells stay zero, the tail estimator refuses non-decaying
factors and respects its cap, and every input validator rejects bad input.

### Validating against real triangles

Synthetic data answers *"does the arithmetic work?"*. It cannot answer
*"how accurate is the estimate?"* — for that you need triangles whose
future is already known.

The **CAS Loss Reserve Database** provides exactly that: Schedule P
triangles for several hundred US insurers across six lines of business,
**with the lower triangle included**, so each accident year's actual
development is available. That turns the tool's estimate into something
scoreable rather than merely plausible.

```bash
python3 data/cas_indir.py --brans ppauto        # download + convert
python3 data/cas_indir.py --brans wkcomp --sirket 43
```

The converter maps CAS's cumulative paid and incurred columns onto the
tool's record schema — paid becomes incremental rows, `incurred − paid`
becomes the outstanding — and holds back the lower triangle as the answer
key. `tests/test_cas_donusum.py` verifies the round trip: rebuilding
`cumulative paid + outstanding` from the converted records reproduces the
original incurred triangle exactly.

One caveat, stated because it matters: CAS data is **annual**, this tool
is quarterly. Accident years are mapped onto consecutive period codes, so
the arithmetic is correct but the report labels one year as one "quarter".

*Data source: [CAS Loss Reserving Data Pulled from NAIC Schedule
P](https://www.casact.org/publications-research/research/research-resources/loss-reserving-data-pulled-naic-schedule-p),
compiled for the CAS by S&P Global Market Intelligence; earlier sets
compiled by Glenn G. Meyers and Peng Shi. Downloaded by the script above;
not redistributed in this repository.*

## Running it

```bash
pip install -r requirements.txt

python3 data/uret.py          # generate the synthetic sample
python3 ibnr.py               # run (GUI if available, else CLI)
pytest -q                     # 21 tests
```

Real data:

```bash
export IBNR_GIRIS_DOSYASI=/path/to/claims.xlsx    # Windows: set ...
python3 ibnr.py
```

### Expected input columns

| Column | Meaning |
|---|---|
| `HasarDonem` | accident quarter, `YYYYQn` |
| `GelDonemHT` | development period, integer quarters |
| `HazAltBrnKod` | branch code (sector-standard, e.g. 715) |
| `Bedeni` | 0 = material, 1 = bodily injury |
| `Havuz` | pool code |
| `HasarDurum` | `Odenen` · `Muallak` · `SovtajRucu` |
| `HasarTutar` | amount |

`Odenen` rows are incremental paid, `Muallak` is the outstanding at that
development point, and the salvage/subrogation sign is configurable
because it differs by source system.

## Known gaps

Listed because they're true, not because they're about to be fixed:

- **No uncertainty measure.** Chain ladder gives a point estimate; the
  obvious next step is the Mack (1993) standard error, then bootstrap ODP
  for the full reserve distribution.
- **One method.** Bornhuetter-Ferguson and Cape Cod are the standard
  alternatives, and chain ladder is unstable for immature accident
  periods where they do better.
- **Single module.** Calculation, reporting and UI share one file.
- **`veri_oku` raises `SystemExit`** on a data error, which is wrong for
  library code — the caller can't catch it. A test documents the current
  behaviour.
